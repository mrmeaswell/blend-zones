# config/

Two files drive the service. Neither requires touching Python.

## workflow.json — the blend zone definition

This is what you edit to fork the service for a new blend zone. It defines
the stages, the fields collected at each one, and what each stage requires
before a ticket can advance:

- `requires.fields` — these field keys must be non-empty
- `requires.signoff` — a person in a `signoff_roles` role must sign off
- `requires.attachments` — N photos/files must be uploaded at that stage

The API enforces these and the frontend renders the fields from this file,
so adding a stage or a field is a config change plus a service restart.
Stage rows are synced into the `stages` table on startup, so the DB and
this file cannot drift apart.

## lti_config.json — Canvas registration

Important: do **not** add comment keys (e.g. `"_comment"`) to this file.
pylti1p3 iterates every top-level key as an issuer and rejects any value
that isn't a list or dict, so a stray string comment makes the whole LTI
provider fail to load with "Invalid tool conf format."

Fill in after registering the Developer Key in Canvas:

1. `client_id` — the Client ID Canvas shows after saving the key
2. `deployment_ids` — the Deployment ID from the app placement
3. The issuer key (`https://canvas.instructure.com`) must match exactly
   what Canvas reports in its LTI 1.3 registration details. Some
   institutions use their own subdomain instead.

Canvas Developer Key URLs for this service (note the `/lti` prefix):

| Canvas field | Value |
|---|---|
| OpenID Connect Initiation URL | `https://<host>/lti/login` |
| Target Link URI | `https://<host>/lti/launch` |
| Public JWK URL | `https://<host>/lti/jwks` |

## keys/

Generated by `scripts/generate_keys.py`. `private.pem` is mode 0600 and
git-ignored. Replacing the keypair invalidates the existing Canvas
Developer Key, which is why the script refuses to overwrite without
`--force`.

## A path gotcha worth knowing

`private_key_file` / `public_key_file` in `lti_config.json` are resolved by
pylti1p3 **relative to the directory containing lti_config.json**, not the
service's working directory. Since both live in `config/`, the correct
values are `keys/private.pem` and `keys/public.pem` — not
`config/keys/private.pem`.
